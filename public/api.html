API Documentation

Base URL: https://nessgate.com. Every endpoint is a public read — no authentication, no API keys, CORS enabled (Access-Control-Allow-Origin: *). Responses are JSON unless noted. NessGate stores nothing; every answer is read on demand from the target domain and cached at the edge for up to 10 minutes.

Resolve a domain

GET /discover/{domain}

Give it any domain. NessGate reads whatever that domain publishes across the standard machine-discovery locations and returns one normalized answer, with a sourceUrl on every record pointing back to the document it came from so you can verify against the domain directly.

Reads run through an adapter architecture with four discovery channels: well-known (fixed paths on the domain), link-rel (a <link rel="ard"> in the homepage), robots (an Agentmap: directive in /robots.txt), and dns (a DoH TXT lookup). The adapters cover llms.txt, ARD / ai-catalog across ARD's normative resolution paths (the well-known catalog and the rel="ard" link, both required by ARD v0.91) plus the robots Agentmap: surface, the A2A agent card, RFC 9727 api-catalog, ai-info.json, OpenAPI, Open Resource Discovery, AWP, RFC 6415 host-meta, Agent Network Protocol (ANP), Universal Commerce Protocol (UCP), AID (a TXT record at _agent.<domain>: v=aid1;…), and GB/Z 185.4 agent descriptions. ANP and UCP are emerging; AID and AWP are drafts. (ARD's in-page JSON-LD and DNS-Service-Binding surfaces, and the separate IETF DNS-AID SVCB draft at _agents.<domain>, are not yet read.) See the specification for the full adapter list.

$ curl https://nessgate.com/discover/example.com

200 OK
{
  "domain": "example.com",
  "provenance": "self-published",
  "note": "These locations are published by the domain itself …",
  "discovered": [
    { "type": "llms.txt", "url": "https://example.com/llms.txt" },
    { "type": "ard-catalog", "url": "https://example.com/.well-known/ard.json" }
  ],
  "resources": [
    { "source": "ard-catalog",
      "sourceUrl": "https://example.com/.well-known/ard.json",
      "type": "application/json",
      "name": "Company data",
      "url": "https://example.com/ai-info.json" }
  ],
  "checked": ["llms.txt","ard-catalog","a2a-agent-card","api-catalog",
              "ai-info.json","openapi","ord","awp","host-meta",
              "anp","ucp","ard-link","ard-agentmap","aid"]
}

400 Bad Request      — input is not a valid domain
429 Too Many Requests — rate limited (120/hour per IP)

discovered is the routing map (which standards the domain publishes, and where). resources is the normalized union of what those documents contain — each record keeps its source standard, the authoritative sourceUrl, an open type label (never a closed set), and, where the source provides them, name/id/raw. checked lists every standard probed, so an empty discovered is still a successful 200 observation. Answers are cached 10 minutes. See the specification for the full contract.

Explore a domain (evidence-based, v2)

GET /explore/{domain}

Everything /discover returns, plus bounded delegated discovery. It follows the explicit machine-readable pointers a domain declares — the links inside an llms.txt index, ARD and api-catalog entries — up to depth 2, crossing to another host only where the publisher itself named the target. It also federates the official MCP Registry for the domain's verified reverse-DNS namespace. Every resource gains an evidence class and a provenance chain:

evidencemeaning
publisher-hostedServed directly by the entered domain.
publisher-declaredA pointer a hosted document explicitly names (possibly on another host).
namespace-verifiedAn external registry (the MCP Registry) verified control of the namespace — attributed to the registry, not re-claimed by NessGate.
candidateA caller-suggested URL (opt-in, below) that NessGate fetched and confirmed is a real machine-readable resource. Its relationship to the domain is unverified — NessGate makes no ownership claim.
publisher-redirect-candidateThe apex homepage redirects to a different registrable domain; recorded with the redirect provenance and only when verified resources exist there — never the same authoritative host.
same-domain-hostA verified resource on a host under the same registrable domain (Organization Discovery, opt-in below). Same registrable domain; the organizational relationship is not independently verified.

Organization Discovery (opt-in). Add ?org=1 to look beyond the exact host: many organizations publish their machine-readable resources on a related subdomain (for example developers.openai.com rather than openai.com). Org mode probes a bounded set of plausible same-domain hosts — subdomains the homepage itself links to, plus a small conventional shortlist (developers, docs, api, …; at most 4 hosts, 2 paths each) — and reports only resources it actually verified, labelled same-domain-host. Hosts probed are listed in orgChecked. No brute-force scanning, no crawling; a host that serves nothing recognized is simply absent. For a related host's full resource graph, explore that host directly.

Related Discovery (opt-in). Add ?related=1 for a clearly separate cross-domain layer, returned in related[] (never mixed with resources[]). Classes: publisher-declared-related — the queried domain itself serves a purpose-built declaration naming the site (a legacy Related Website Set file or a Digital Asset Links web statement; hyperlinks never qualify), with a mutual flag when the site reciprocates; registry-verified-related — a domain-verifying registry (the MCP Registry) names the specific host, always attributed; infrastructure-correlated-candidate — caller-supplied candidates with a cited technical signal. Technical signals (nameserver containment, …) appear in signals[] as corroboration only — they never mean "official" or "same organization". Bounded (≤5 hosts) and best-effort; full rules in docs/related-discovery-rules.md.

Known limitation of the hosted resolver: some sites' bot protection challenges requests from shared cloud infrastructure, so the hosted endpoints can miss files those sites do publish (they are reported as not found, never guessed). The embeddable library, running from your own environment, does not share this limitation.

Opt-in candidate verification. POST /explore/{domain} with a JSON body {"candidates":["https://…", …]} lets your own AI/search suggest resource URLs; NessGate fetches each (bounded, SSRF-checked), verifies it is genuinely machine-readable, and returns only those, labelled evidence:"candidate" with ["ai-candidate", url] provenance. NessGate runs no AI and stores nothing — the principle is AI suggests, NessGate verifies; NessGate never decides ownership. Up to 10 candidates per request; these responses are never cached. The plain GET stays fully deterministic.

Response adds federated, per-record evidence/provenance/depth, and stats (counts, requests, hosts, bytes, truncated). It is strictly bounded — depth ≤2, ≤8 hosts, ≤24 requests, a global byte cap, and the same SSRF checks on every cross-host hop — and, like /discover, stores nothing, crawls nothing, guesses no subdomains, runs no AI, and makes no ownership claim. /discover is unchanged for existing integrations.

Run the resolver yourself

The same normalization is available as a dependency-free library that fetches target domains directly, with no runtime dependency on nessgate.com:

npm i @nessgate/resolver

import { resolve } from "@nessgate/resolver";
const { resources } = await resolve("example.com");

Or import it straight from the edge: import { resolve } from "https://nessgate.com/resolver.mjs". Source and package: GitHub · npm.

MCP server (for AI agents)

POST /mcp          — Model Context Protocol, Streamable HTTP transport

AI agents can call the resolver natively over the Model Context Protocol instead of the REST API. The server is stateless, requires no authentication, and exposes one read-only tool that dispatches to the same handler (and rate limits) as /discover:

ToolReturns
discover_domainThe normalized machine-readable resources the domain publishes (same answer as /discover/{domain}), with a sourceUrl on each record.
$ curl -X POST https://nessgate.com/mcp -H "Content-Type: application/json" -d '{
    "jsonrpc": "2.0", "id": 1, "method": "tools/call",
    "params": { "name": "discover_domain",
                "arguments": { "domain": "example.com" } } }'

Connect from an MCP client with transport type streamable-http and URL https://nessgate.com/mcp. Sessions and server-initiated streams are not used, and batching is not supported.

Human-readable pages

GET /{domain}          e.g. https://nessgate.com/example.com

A live HTML view of what a domain publishes — the resolver rendered for humans. Machine discovery: /sitemap.xml and /robots.txt.

NessGate's own declaration

NessGate reads these standards on other domains, so it publishes its own where meaningful: /llms.txt, an RFC 9727 API catalog at /.well-known/api-catalog, /ai-info.json, and an OpenAPI description at /openapi.json. It does not publish an A2A agent card, because NessGate is not an A2A agent — publishing artifacts that describe nothing real is exactly what this project exists to discourage.

Machine-readable API description

An OpenAPI 3.0 description of this API is available at /openapi.json for client generation and tooling, and is linked from the RFC 9727 catalog at /.well-known/api-catalog.
