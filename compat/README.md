# NessGate Compatibility Corpus

This directory is the **moat**: accumulated, permanent compatibility knowledge. See
`../docs/compatibility-foundation.md` for the full strategy. The guiding line:

> NessGate's moat is not knowing every domain in advance; it is knowing how to resolve domains it
> has never seen before.

## Layout

- `matrix.json` — machine-readable protocol × version support matrix (surfaces, parser, authority,
  official suite, known deviations, fixtures). The single source of truth for any "supports X" claim.
- `adapters/<id>.json` — one contract manifest per resolver adapter (surfaces, versions, authority
  semantics, `canEstablishAuthority`, provenance requirement, official suite, deviations, fixtures).
- `fixtures/<protocol>/<version>/<case>.json` — document-level regression cases (no network). A
  `positive` fixture asserts the normalized records; a `reject` fixture asserts the document is
  correctly refused (catch-alls, HTML shells, wrong shape).
- `metrics.json` — generated by `npm run compat:matrix` (engineering metrics; no confidence scores).

Fixtures are **document-level, not domain-level** — we test *how a document is read*, so there is
nothing to "memorize" about specific sites. The moat's other half — *resolving unseen domains* — is
measured separately and independently by `../benchmarks/bench-unseen.mjs` against a frozen holdout.

## The rule (enforced in CI and review)

> **Never fix a compatibility problem only in code. Every real compatibility fix MUST add a
> permanent regression fixture here.** A code fix without a fixture fails review.

If a holdout (unseen-benchmark) domain teaches a fix: retire it from the holdout, turn the lesson
into a fixture here, and add a fresh unseen domain to the holdout — never tune against the holdout.

## Fixture format

```json
{
  "id": "ard-catalog/0.91/basic-url-entry",
  "protocol": "ard-catalog", "version": "0.91", "surface": "/.well-known/ard.json", "kind": "json",
  "origin": "official-example | reference-impl | real-world | synthetic",
  "input":  { "url": "https://x.com/.well-known/ard.json", "body": "…" },
  "expect": { "relationship": "publisher-hosted", "level": 1,
              "resources": [ { "source": "ard-catalog", "type": "…", "url": "…" } ] },
  "notes": "why this case exists / the quirk"
}
```
For a `reject` fixture, use `"expect": { "reject": true }`.

## Running

- `npm run test:compat` — run every fixture (layer 2: real-world compatibility).
- `npm run compat:matrix` — matrix/adapter/fixture consistency + emit `metrics.json`.
Both are part of `npm run check` and the pre-deploy gate.

## Provenance of the seed set

The initial fixtures were backfilled from the resolver's existing hand-written normalization tests
and the live `ADAPTERS` array by `_generate-seed.mjs` (kept for provenance; not part of CI). All
**new** fixtures are added by hand under the rule above.

Layer 1 (official schemas / conformance vectors ingested from each ecosystem) arrives in M2.
