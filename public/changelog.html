Changelog

Notable changes to the NessGate resolver and its specification, newest first. Specification stability guarantees live in the specification.

2026

Opt-in reachability verification (?verify=1)

  • Finding an address does not mean an agent can use it. ?verify=1 (and the library's resolve(domain, {verify: true})) adds per-record reachability — ok / auth-required / not-found / unreachable — with checkedAt, distinguishing outages from auth walls from dead declarations. Evidence-derived where possible: already-fetched surfaces are ok with no extra request, MCP records reuse introspection, and only declared pointers get one safe probe each (HEAD, then a bounded GET — never a POST, never an execution), capped at 8. ok asserts only that the endpoint answered a safe request; absent reachability means not checked. Off by default; additive; library 1.11.0.

Seven fixes from an adversarial component evaluation

  • An isolated evaluation (deterministic adversarial scenario suite + unseen live domains + free-tool comparisons) demonstrated seven concrete weaknesses; each fix ships with its demonstrating scenario as a regression test. Discovery: YAML OpenAPI specs (/openapi.yaml/.yml) are now detected via the document's own top-level marker (pointer records, verbatim title — no capability enumeration without a YAML parser, stated plainly); the llms-full.txt companion location is probed; one catalog declared through several channels (well-known + rel="ard" + robots Agentmap) now yields one record, not three (both hosted and library). Library robustness: a global deadlineMs budget (default 20 s — the hosted worker always had one; the library did not), with empty cut-short results labeled incomplete; a nonexistent probed host (DNS NXDOMAIN) now counts as an answer rather than a refusal; a transient apex DNS failure is retried once before it can read as nonexistence. New library capability: resolve(domain, {org: true}) — bounded related-host discovery (docs./developers./…), the in-process counterpart of /explore?org=1, reporting orgChecked. Library 1.10.0; all changes additive.

Unified outcome label: found / none-found / blocked / incomplete

  • Every /discover and /explore response (and the library's resolve()) now carries a single outcome label, derived from a classification of every failed probe: a clean 404/410, a nonexistent host, or a redirect pointing away is an answer (absence confirmed at that location); an auth wall, rate limit, timeout, or network failure is a refusal (absence unknown). Nothing found + refusals at least as common as answers → blocked, never a silent empty. /explore adds incomplete when budgets cut the walk short, and blockedProbes discloses refusal counts even under none-found. The homepage checker now says explicitly when a domain would not let hosted checks look. Additive; existing fields unchanged.

Related-host check: probe slots go to plausible publishing hosts

  • /explore/{domain}?org=1 probes a bounded set of same-domain hosts. Host selection is now prioritized: homepage-linked hosts with developer/documentation-facing labels (docs., developers., api., platform., community., …) first, then the conventional shortlist, then remaining homepage-linked hosts — so CDN/telemetry/navigation subdomains that happen to appear first in the homepage HTML no longer consume the probe budget. Probes now also include /.well-known/ai-catalog.json (the ARD-canonical name). Prioritization only orders the bounded probe list; a host is still reported only when it serves a validated machine-readable document. The homepage check UI now lists exactly which hosts were checked when nothing is found, and distinguishes rate limiting from a timeout.
  • When the queried domain's own homepage redirects to a different registrable domain (aws.com → aws.amazon.com), the org response now reports it as homepageRedirect — an honest observation of the publisher's own configuration, never merged into resources — and the homepage UI offers a one-click "Check {target} →" follow-through. Shell domains stop reading as bare, unexplained empties.
  • Probe set widened: cloud. joined the conventional shortlist (cloud.google.com serves llms.txt while docs./developers.google.com do not) and the host cap rose from 4 to 6, still inside the request budget. Org responses also gain orgBlocked: hosts whose probes were all refused or blackholed (network failure, 401/403/405/429, 5xx) — a clean 404 still counts as "answered, publishes nothing". The UI reports blocked hosts as absence unknown (the embeddable library from your own machine may succeed) instead of implying "nothing found".

Opt-in read-only MCP introspection (?mcp=1)

  • When a domain declares an MCP endpoint, /discover/{domain}?mcp=1 (and the library's resolve(domain, {mcp: true})) can ask that server what it declares, using the protocol's own read-only handshake: initialize and tools/list — nothing else, ever. No tool execution, no credentials (auth walls are labeled auth-required, never retried), POSTs never follow redirects, HTTPS endpoints on the queried registrable domain only, max 3 per resolution, 256 KB response cap. Declared tools (name/description/inputSchema) land verbatim in the existing capabilities envelope; introspection records the negotiated protocol version and serverInfo; responses are labeled introspected:["mcp"]. Off by default — the default response never introspects. Additive; library 1.8.0.

Declared capabilities on resources (verbatim) + honest redirect attribution in the library

  • /discover resources (and the library's resolve()) can now carry a capabilities array copied 1:1 from the publisher's own declarations: OpenAPI operations (method, path, operationId, summary) with declared security schemes, and A2A / GB‑Z agent-card skills. Nothing is inferred, renamed, or reclassified — a source that declares nothing simply has no capabilities field. Lists cap at 40 with a labeled capabilitiesTruncated flag. For OpenAPI documents larger than the 64 KB detection prefix, one additional bounded read (1 MB) enumerates operations; larger specs stay detected-but-not-enumerated.
  • The embeddable library (@nessgate/resolver 1.7.0) now records the final post-redirect URL as sourceUrl and labels a fetched document whose final URL crossed to a different registrable domain verified-external-location instead of verified-publisher-location — accurate attribution for wholesale rebrands (e.g. neon.tech → neon.com). The hosted resolver remains domain-locked and never follows cross-domain redirects. Additive; existing fields are unchanged.

Charter amended — anonymous operational measurement of discovery fulfilment

  • Charter Promise 6 and the Privacy Policy now permit NessGate to record anonymous, categorical events about its own operation: for each discovery call, one outcome label — resources returned, none returned, invalid input, or error — with a timestamp and nothing else. There are no domains, request contents, IP addresses, or identities, and no client-IP classification. Cloudflare Analytics Engine stores these events, aggregates them when queried, may sample them, and retains them for about three months. The sole purpose is to measure whether NessGate actually returns results to agents; it never captures who calls or what they look up, and never influences how any resource is classified. Domain data, user data, cookies, and visitor tracking remain prohibited.

Proposed Charter v2 — draft published for review (not yet effective)

  • A proposed Charter v2 is published as a public draft. It is not yet effective and changes nothing about how the resolver behaves today; Charter v1 remains the active, binding charter. The draft proposes two clearly separated kinds of state (publisher-declared/registered records and a short-lived discovery cache), provenance-scoped publisher control, bounded reading of a publisher's own pages plus defined public adapters, grouped-not-ranked ordering, and seven affirmative neutrality promises. Production behavior will not adopt any of these before Charter v2 becomes the active charter. Technical design: docs/v2-architecture.md.

v1.6.0 — Benchmark-driven general rules

  • Canonical-host fallback (same registrable domain only). When the exact host publishes nothing and its homepage redirects to www./a subdomain of itself, /discover (and the library) probes that canonical host for llms.txt and ard.json. Cross-registrable-domain redirects are never followed here.
  • Stricter text-probe validation. HTML is now detected behind leading <!-- --> comments, closing a false positive where an HTML login shell could pass as llms.txt; genuine text files with comment headers still pass.
  • publisher-redirect-candidate. In Related Discovery, an apex homepage redirecting to a different registrable domain yields a provenance-carrying candidate entry (verified resources required) — never treated as the same authoritative host.
  • Heavy-route CPU cut: documents are parsed once and shape-checked as objects, instead of re-parsed per candidate type.

v1.5.0 — Related Discovery

  • GET /explore/{domain}?related=1 (opt-in). A clearly separate cross-registrable-domain layer, returned in related[] and never mixed with exact-host results. publisher-declared-related: the queried domain itself serves a purpose-built declaration naming the site (a legacy Related Website Set file, checked for reciprocity, or a Digital Asset Links web statement) — hyperlinks never qualify. registry-verified-related: a domain-verifying registry names the specific host, always attributed. infrastructure-correlated-candidate: caller-supplied candidates with a cited technical signal. Technical signals (nameserver containment) are recorded in signals[] as corroboration only — they never mean "official" or "same organization", alone or combined. Bounded (≤5 related hosts), deterministic, non-crawling; evidence rules in docs/related-discovery-rules.md.

v1.4.0 — Organization Discovery

  • GET /explore/{domain}?org=1 (opt-in). Many organizations publish their machine-readable resources on a related subdomain (developers.openai.com) rather than the apex. Organization Discovery probes a bounded set of plausible same-registrable-domain hosts — subdomains the homepage itself links to, plus a small conventional shortlist (at most 4 hosts × 2 paths) — and reports only resources that actually verify, labelled evidence same-domain-host with the probe provenance. The registrable domain is shared; the organizational relationship is not independently verified. Hosts probed appear in orgChecked. No brute-force scanning; off by default; /discover and default /explore unchanged.

v1.3.3 — Documentation

  • Corrected the npm package README: current mechanism list, accurate export names, browser guidance (use the hosted endpoint for arbitrary domains), and the optional GB/Z 185.5 gateway option. No behavior change.

v1.3.2 — Evidence-based exploration; version alignment

  • GET /explore/{domain} (additive). Everything /discover returns, plus bounded delegated discovery: NessGate follows the explicit machine-readable pointers a domain declares (an llms.txt index's links, ARD and api-catalog entries) up to depth 2 — cross-host only where the publisher named the target — and federates the official MCP Registry for the domain's verified reverse-DNS namespace. Every record carries an evidence class (publisher-hosted / publisher-declared / namespace-verified / candidate) and a provenance chain. Strictly bounded (depth ≤2, ≤8 hosts, ≤24 requests, global byte cap, SSRF checks on every hop); stateless; no crawling, no guessed subdomains, no ownership claim. /discover is unchanged.
  • Opt-in candidate verification. POST /explore/{domain} with {"candidates":[…]} verifies caller-suggested URLs (from the caller's own AI or search) and labels each evidence:"candidate" — existence and type confirmed, relationship to the domain unverified. NessGate itself runs no AI.
  • Honest empty results. An empty answer now reads "no supported resources found on this exact host", noting that related product hosts or external registries may publish more.
  • Version labels aligned across the library, MCP server, registry listing, and this API description. No behavior change.

v1.3.1 — Accuracy fixes

  • AID, not DNS-AID. The DNS adapter reads the AID draft's TXT record (v=aid1 at _agent); it is not the IETF DNS-AID draft (SVCB at _agents), which is a separate, unimplemented mechanism. The adapter id changed from dns-aid to aid.
  • ARD scope narrowed. NessGate implements ARD's normative domain resolution (well-known catalog + rel="ard", both MUST in v0.91) plus the robots Agentmap: surface; in-page JSON-LD and the not-yet-specified DNS mechanism are not read.

v1.3.0 — GB/Z 185.4 agent descriptions

  • GB/Z 185.4 (China, 智能体互联). ACS agent descriptions are recognized by content and normalized (source gbz-185-4), preserving aic, provider, security schemes, certificate, and skills. No GB/Z-specific path is guessed. The embeddable library adds an optional, Node-only GB/Z 185.5 gateway query against a caller-configured endpoint with caller-supplied authentication.

v1.2.0 — Universal resolver: adapter architecture

  • Fourteen adapters over four channels (well-known paths, the ARD rel="ard" link, the robots Agentmap: directive, and a DNS TXT lookup): adds ANP agent descriptions, UCP merchant profiles, the AID TXT record, and the two additional ARD surfaces to the original set. Listed in the official MCP Registry as com.nessgate/nessgate.

v1.1.0 — Initial public release

  • The neutral resolver. GET /discover/{domain} reads whatever a domain publishes across the supported machine-discovery locations (ARD / ai-catalog.json, A2A agent card, llms.txt, RFC 9727 api-catalog, ai-info.json, OpenAPI, Open Resource Discovery, host-meta) and returns one normalized answer, with a link back to each source so an agent can read the domain directly. NessGate reads these; it does not define or replace them.
  • Embeddable library. A dependency-free resolver at /resolver.mjs and on npm as @nessgate/resolver, running in browsers, Node, Deno, Workers, and agent runtimes with no runtime dependency on nessgate.com. The same lookup is available as the discover_domain MCP tool at /mcp.
  • Open and neutral. Open specification, Apache-2.0 reference implementation, governed by the Charter: free forever, neutral, no accounts, no ranking, no lock-in, stores nothing.
